# Open Questions

What the sources leave unsettled, with the rule that would close each. None of these blocks the verification-foundation milestone; each names the milestone or record that would answer it. [ADR 0015](../../adr/0015-generator-verifier-development-model.md) lists the ones it declined to decide.

| Question | Why it is open | Closure rule |
| --- | --- | --- |
| Which bounded verifier, Kani or Verus, gets the first harness on one pure predicate? | ADR 0007 §6 asks for one harness with cover checks before wider adoption. VeruSAGE and ExVerus show agents can complete Verus proofs given a specification and can cheat without a checker; nothing measured Kani in the same setting. | The Assessment Kernel milestone runs one predicate through one of them, records cost, vacuity checks, and the escape hatches the tool admits, and the record decides. |
| Does the escape-hatch scan need to be semantic? | VeruSAGE's cheat checker and Baker et al.'s catalogue are syntactic and worked in their settings. A weakened postcondition inside a `deny` block, or a test rewritten to assert a tautology, passes a substring scan. The `weakened-gate` fixture shows the gate names such a commit only because it is an undeclared verifier change, not because it saw the weakening. | Stays a review item under rule 11 until a case arrives that the scan and the review both missed; that case becomes a fixture and the record says whether a semantic check would have caught it. |
| How much generator variance is there on a kernel property? | Turbulence measured it on self-contained problems. No measurement exists for a Rust invariant with a fixed oracle. | `generator-variance`, once one kernel function and its oracle exist. Exploratory; its result never gates. |
| What does mutation testing cost on a kernel crate? | The calibration ran on the tooling crate, whose tests drive Cargo and Git. A kernel crate's tests are pure and run without subprocesses, but its mutant count is unknown. | Rerun the calibration on the Assessment Kernel and record runtime, counts, and the survivor classification. |
| Are model-generated mutants worth the equivalence cost? | Wang et al. and LLMorpheus report higher fault detection at higher non-compiling and equivalent rates, for Java and JavaScript. | Not before the semantic corpus is active. If a survivor class the corpus misses recurs, try one model-generated batch on one module and classify by hand. |
| Should receipts be signed? | Receipts are traceable, not tamper-proof. Proof-carrying code moves trust to a small checker; a signature moves it to a key. Nobody has asked who would hold the key. | Not decided. Reopen when a receipt from outside the repository, such as a scheduled mutation run, must be trusted by a gate. |
| Should a Plan carry a witness the Cell can check? | Proof-carrying code's mechanism fits the Warp boundary. ADR 0014 defers witnesses until a baseline planner exists to check against. | ADR 0014's revisit trigger. |
| Can the generated-test bias be measured here? | Konstantinou et al. measured oracle accuracy on correct and buggy Java code. Nothing similar exists for Rust or for invariant-shaped properties. | Inside `generator-variance`: the same candidates judged by their own generated tests and by the fixed oracle, with the disagreement rate recorded. |
| Which metamorphic relations exist for Assessment and Warp? | The technique is general; the relations are specific and unwritten. Permutation invariance follows from N12 and monotonicity of Indeterminate from N13; the rest need the kernels. | Each kernel milestone states its relations in its result card before its tests exist. |
| Does a squash merge lose trust-boundary declarations? | The gate reads `Trust-Boundary:` lines from each non-merge commit. A squash writes one commit whose message is whatever the merger typed. | Policy: this repository merges with merge commits. Reopen if the hosting platform's squash default is ever enabled. |
